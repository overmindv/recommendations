# Офлайн-проверка учебных планов

Набор [«Алгоритмы и структуры данных»](../evaluation/algorithms.json) содержит
восемь синтетических случаев. Цели, расписание и ожидаемые проверки заданы
вручную. Экспертных оценок пока нет. Набор не импортируется в каталог пилота.

## Запуск

```sh
go run ./cmd/plan-eval -cases evaluation/algorithms.json
go test ./internal/evaluation ./cmd/plan-eval
go test ./internal/evaluation -run '^$' -bench '^BenchmarkEvaluate$' -benchmem
```

Команда читает локальный JSON и печатает отчет. Сервис, сеть и БД не нужны.
Код выхода собранного бинарника: `0` при успешной проверке, `1` при нарушениях
или расхождении с ожиданиями, `2` при ошибке входа или выполнения. При
расхождении отчет остается доступен на stdout.

## Что сравниваем

- Адаптивный вариант запускает `BuildLearningPlan` с версионированной
  политикой, известными оценками и подсказками по сложности.
- Фиксированный вариант идет по `curriculum`, без замены материалов и
  перестановки тем. При невозможности запланировать модуль целиком он
  фиксирует пробел. Бюджет, пререквизиты и правила доступа те же.
- Перед расчетом обе стратегии получают только события, у которых
  `observed_at` и `available_at` не позже `as_of`. Активна опубликованная к
  этой дате и еще не отозванная ревизия ресурса. Раздел `holdout` начинается
  с `holdout_from` включительно; политика фиксирована для обеих групп.
  Ожидания и экспертные баллы в планировщик не передаются.

Покрытая цель означает достаточную прошлую оценку или запланированную
допустимую независимую проверку. Запланированная проверка не подтверждает
освоение темы. Для каждого случая видны шаги, пробелы, минуты, число тем,
видов ресурсов и уровней сложности.

Порог для автоматической проверки: ни одного запрещенного ресурса,
нарушения графа, отсутствующего условия перехода или превышения бюджета.
Отдельно сверяются ожидаемые проверки и причины пробелов адаптивного
плана. Ошибки выводятся с номером шага и условным названием темы.

## Результат на текущем наборе

| Группа | Случаи | Покрыто: адаптивный / фиксированный | Минуты: адаптивный / фиксированный | Нарушения |
| --- | ---: | ---: | ---: | ---: |
| Development | 3 | 2/3 / 2/3 | 79 / 80 | 0 |
| Holdout | 5 | 3/5 / 1/5 | 164 / 137 | 0 |

Разница в holdout получилась на двух примерах: известный пререквизит не
занял бюджет повторно, а недоступный материал удалось заменить. При
отсутствии доступной независимой проверки оба варианта оставили пробел.
Это ручные примеры регрессий, а не выборка студентов или измерение
учебного эффекта.

## Экспертная проверка

Рецензент сначала проверяет граф, время и ожидаемые этапы, затем сравнивает
два расписания без названий методов. В поле `expert_review` можно указать
версию шкалы (`rubric`), дату (`reviewed_at`) и баллы от 1 до 5 для
`adaptive` и `static`. Для первой шкалы: 1 означает непригодный план,
3 означает пригодный после правок, 5 означает пригодный без правок.
Оценки не включаются в автоматический порог. После изменения расписания
их нужно пересмотреть, а не переносить на новую версию.

До рецензии `expert_rated_cases` равен нулю. В набор не добавляются реальные
профили, исходники решений, скрытые тесты и выгрузки с учебной историей.
