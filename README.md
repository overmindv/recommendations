# recommendations

Внутренний сервис предварительной подборки практики. Пользователь выбирает
1–5 тем и бюджет 10–240 минут; gateway передаёт разрешённые опубликованные задачи,
активные темы с полным графом prerequisites и историю только проверенного actor.
Сервис не читает чужие БД. Предварительная подборка остается stateless;
при заданном `DATABASE_URL` отдельная PostgreSQL хранит цели практики, планы и
данные учебных целей. Проверка каталога задач и материалов включается отдельно.
Маршрут на 1-8 занятий поддерживается политикой practice-v3.

Внутренний API [диагностики](docs/diagnostic.md) подбирает задачи для сохраненной
учебной цели и закрепляет их версии в сессии.

При включенном [приеме учебных событий](docs/learning-evidence.md) сервис
сохраняет оценки Tasks и подтверждения чтения Content в собственной базе.

Это прозрачная эвристика для выбора следующей практики, **не модель освоения** и не
вероятность знания. Три accepted — лишь правило допуска к практике зависимой темы;
оно не доказывает обучение и не выдаёт сертификатов/наград. `tasks.md` — проектный
проектный backlog, его карточки не являются перечнем завершённых возможностей.

## Запуск и проверки

Требуется Go 1.26+. Каркас `github.com/overmindv/parker v0.1.0` подключён по тегу.

```sh
export RECOMMENDATIONS_SERVICE_TOKEN="$(openssl rand -hex 32)"
export DATABASE_URL='postgres://recommendations:...@localhost:5438/recommendations?sslmode=disable'
make migrate-up
make run
make lint
make test
make build
make benchmark
```

Компонентная проверка цели выполняется только на выделенной базе после
`make migrate-up`: `GOALS_TEST_DSN='postgres://.../goals_component?sslmode=disable' make ctest`.
Тест удаляет только собственные записи; не направлять его на общую или production БД.
Результаты проверки этого среза: `docs/verification-goals.md`.

Секрет gateway должен совпадать. Не сохранять токен в git, отчётах или логах.
Docker: `docker build -t recommendations .`; запуск — с переменной токена и внутренней
сетью. Публикация внутреннего API в интернет не предусмотрена. Деплой не входит в MVP.

| Переменная | Правило |
| --- | --- |
| `RECOMMENDATIONS_SERVICE_TOKEN` | Обязательна, 32–4096 байт, без пробелов; случайный секрет |
| `DATABASE_URL` | PostgreSQL сервиса для сохранённых целей; без неё preview работает, а API целей возвращает 503 |
| `HTTP_ADDRESS` | Адрес `host:port`, приоритет над `HTTP_ADDR` |
| `HTTP_ADDR` | Стандартный адрес parker; приоритет над `PORT` |
| `PORT` | Совместимость с Railway: `:PORT`; по умолчанию `:8080` |
| `READ_TIMEOUT`, `WRITE_TIMEOUT`, `SHUTDOWN_TIMEOUT` | parker: `10s`, `20s`, `10s` |
| `METRICS_ENABLED`, `PPROF_ENABLED`, `LOG_LEVEL` | parker: `true`, `false`, `info` |

Parker предоставляет `GET /health`, `GET /ready`, `GET /metrics`, request IDs,
обезличенные access logs и graceful shutdown. При `DATABASE_URL` добавляется
health-check PostgreSQL; Kafka не используется. Read-header timeout — 5s, idle timeout — 60s;
HTTP-обработчик ограничен 3s. Метрики HTTP не содержат user/task IDs. Профили и тела
запросов не логируются; ответы содержат `Cache-Control: no-store`.

На PR запускаются линтер, тесты, сборка и бенчмарки. Перед релизом запустите
[Check release candidate](https://github.com/overmindv/infra/actions/workflows/release-e2e.yml)
в Infra с содержимым `release.json` от кандидата. Прогон проверяет образы из
манифеста и запускает сценарии API и браузера. Файл `observed-release.json`
показывает, какие образы запустились. Для приемки нужен успешный прогон целиком.

из исходников.

## Граф каталога

При заданных `ENTITIES_URL` и `ENTITIES_SNAPSHOT_TOKEN` процесс восстанавливает
локальный граф тем из Entities. Нужна PostgreSQL с миграциями Recommendations.
Пока токен не настроен, синхронизация выключена, старые маршруты не меняются.
Используйте отдельный токен чтения снимка, одинаковый в Entities и Recommendations.

Снимок загружается страницами на одной версии и становится доступным после
проверки ссылок и циклов. Затем процесс читает журнал `/changes`. Inbox,
изменения графа и позиция `through` фиксируются вместе. После сбоя выгрузка
продолжается с сохраненной позиции.

Некорректная страница попадает в карантин. Новые записи из этой страницы не
публикуются, а предыдущая проверенная версия остается доступной. Процесс
запрашивает свежий снимок. Удаленные темы не отображаются в пререквизитах даже
если их связи еще есть в Entities. Планировщик пока не использует эту проекцию.

Компонентная проверка требует `GOALS_TEST_DSN` с выделенной базой `_test`
и примененными миграциями:

```bash
go test -race ./internal/projection/catalog -run TestPostgresCurriculumProjection
go test ./internal/projection/catalog -run '^$' -bench 'Benchmark(Snapshot|Replay)Page200' -benchmem
```

## Учебные цели

`internal/learnergoals` хранит один недельный бюджет и часовой пояс пользователя.
Активные цели делят этот бюджет: сумма их долей не может превышать доступные минуты.
Неактивная или удаленная цель не занимает бюджет. Истекший срок не снимает бронь
сам: цель можно деактивировать или продлить. Срок хранится как календарная дата
в часовом поясе пользователя, а не как момент времени в UTC.

Хранилище принимает проверенный ID владельца отдельно от данных цели. Записи
требуют ожидаемую версию, а для новой доступности используют версию `0`. Повтор
того же запроса в течение 24 часов возвращает первый успешный результат.
Использование того же ID с другими данными отклоняется. На пользователя
допускается до 32 целей и 256 успешных записей за окно повторов.

Языки, форматы и самооценка хранятся в настройках цели. Для темы без самооценки
записывается `unknown`. Эти данные не меняют доказанный уровень знаний.
Миграция `202611180001` не меняет существующие цели практики. Сервис раз в минуту
удаляет не больше 1000 просроченных ключей.

Внутренний HTTP-контракт: [api/openapi.yaml](api/openapi.yaml).
`GET /v1/learner/goal-templates` отдает версии шаблонов.
`GET /v1/learner/profile` возвращает `availability: null` до первого сохранения
профиля. `GET /v1/learner/goals` в этом случае возвращает пустой список.
Это учебный профиль, он не меняет учетную запись в Users. Профиль и цели
доступны только с токеном gateway и доверенным `X-User-ID`.
Для записи нужен UUID в `Idempotency-Key`. Для изменения и удаления нужен
`X-Expected-Version`, при создании профиля он равен `0`.

Задайте `ENTITIES_URL` на внутренний HTTP-адрес Entities. Создание и изменение
цели проверяют до 16 опубликованных тем, не больше четырех запросов параллельно.
При недоступном каталоге новые записи возвращают `503`, но сохраненный повтор
отдается из БД. Без истории состояние навыков `unknown`, независимо от самооценки.
Пока нет оценки плана, возвращается `not_evaluated`, а прошедший срок отмечается
как `infeasible`. Старый `/v1/practice-goal` не меняется.

## Сохраненная цель практики

С тем же service token и доверенным `X-User-ID`: `GET /v1/practice-goal` возвращает
цель или 404, `PUT /v1/practice-goal` заменяет её и увеличивает revision,
`DELETE /v1/practice-goal` идемпотентно удаляет. PUT принимает только
`{"topic_ids":["uuid"],"minutes":60}`: 1–5 уникальных UUID и 10–240 минут.
До записи gateway проверяет, что темы активны и граф prerequisites корректен.
Другой actor не может прочитать или изменить цель. При отсутствии БД или ошибке
чтения возвращается 503, а не пустая цель. Цель не хранит оценку знаний: при
возвращении на страницу gateway заново строит preview по текущим решениям.

## Контракт

`POST /v1/practice-plan`, `Content-Type: application/json`,
`Authorization: Bearer <service token>`, `X-User-ID: <trusted actor UUID>`.
Проверяется digest токена constant-time сравнением. UUID — канонические строчные,
не нулевые. Источник actor — проверенный JWT gateway, поля actor в JSON нет.

```json
{
  "topic_ids": ["00000000-0000-0000-0000-000000000001"],
  "minutes": 60,
  "topics": [{"id":"00000000-0000-0000-0000-000000000001", "prerequisite_ids":[]}],
  "tasks": [{"id":"00000000-0000-0000-0000-000000000002", "task_version_id":"00000000-0000-0000-0000-000000000003", "topic_id":"00000000-0000-0000-0000-000000000001", "title":"Первая задача", "difficulty":"easy", "task_type":"single_choice"}],
  "evidence": [],
  "input_truncated": false
}
```

```json
{"policy_version":"practice-v2","total_minutes":10,"warnings":[],"items":[{"task_id":"00000000-0000-0000-0000-000000000002","task_version_id":"00000000-0000-0000-0000-000000000003","topic_id":"00000000-0000-0000-0000-000000000001","title":"Первая задача","difficulty":"easy","task_type":"single_choice","estimated_minutes":10,"reason_code":"START_TOPIC"}]}
```

Evidence содержит `task_id`, `task_version_id`, `verdict`, `occurred_at` (RFC3339).
Публикацию, доступность, active topics и принадлежность истории проверяет gateway,
поскольку в этом сервисе нет источников истины этих признаков. Ответ не содержит
решений, правильных ответов, тестов и скрытых данных. Ошибка зависимости gateway
не превращается в пустую историю.

Лимиты: 32 темы вместе с prerequisite closure, 2000 задач, 2000 объединённых evidence
(до 1000 choice и 1000 code у gateway), 2000 байт заголовка задачи, 4 MiB JSON,
20 задач в ответе. Неизвестные поля, лишний JSON после объекта, дубликаты task/topic/version,
неизвестная тема, циклический/неполный граф, неподдерживаемый verdict/type/difficulty
отвергаются. Повторы evidence разрешены и не увеличивают вес. История удалённых или
старых версий допустима на входе, но не влияет на план.

Ошибки JSON: `{ "code": "INVALID_ARGUMENT", "message": "Invalid practice plan request" }`.
HTTP: 400 — некорректные данные, 403 — неверный токен/actor, 413 — размер, 415 — media type,
503 — deadline/cancellation. Ошибки не включают значения входа. GraphQL BFF переводит
snake_case в camelCase и возвращает обезличенные сообщения пользователю.

## Политика `practice-v2`

1. Рассматривать только evidence текущей версии задач каталога. Любой accepted этой
   версии исключает задачу из плана; поздняя ошибочная попытка не отменяет accepted.
   Accepted одной task/version считается один раз; исправления/rejudge пока не поддержаны.
2. Wrong answer, compilation/runtime/time/memory/output errors отмечают потребность
   в практике, по одному признаку на нерешённую задачу. Infrastructure/checker errors
   и cancelled нейтральны. Время попытки валидируется, но временное затухание не применяется.
3. Prerequisite допускает следующую тему после **трёх разных accepted задач текущих
   версий**. Все транзитивные prerequisites тоже должны быть готовы. При недостатке
   evidence сначала предлагаются доступные основания графа, причина `PREREQUISITE`.
   Добавление задач в план не открывает следующие темы: нужны реальные результаты.
4. Cold start и 1–2 accepted: только easy. От 3 accepted доступны medium, от 6 — hard.
   При любой нерешённой задаче с ошибкой верхняя сложность снижается на один уровень.
   Более лёгкие задачи остаются допустимы; слишком сложные не используются как fallback.
5. После ошибки в теме сначала предлагается новая подходящая задача этой темы;
   нерешённая задача с ошибкой остаётся запасным вариантом. После каждого выбора
   преимущество получает тема с меньшим числом выбранных задач. Внутри темы выбирается
   менее представленный тип задачи, затем ближайшая допустимая сложность и
   лексикографический task ID. Входной порядок не меняет результат.
6. Жадный выбор берёт только помещающиеся в остаток бюджета задачи, максимум 20.
   Оценки времени — экспертные стартовые значения, а не измеренная длительность:

| Тип | easy | medium | hard |
| --- | ---: | ---: | ---: |
| single_choice / multiple_choice | 10 | 15 | 20 |
| programming | 20 | 35 | 50 |

Причины: `START_TOPIC` — нет accepted и пробелов; `PRACTICE_GAP` — нерешённые ошибки;
`NEXT_CHALLENGE` — есть accepted; `PREREQUISITE` — доступная база заблокированной цели
(имеет приоритет над другими причинами). Результат не подразумевает completion цели.

Warnings возвращаются в стабильном порядке: `PARTIAL_DATA` при усечённом входе;
`PREREQUISITE_GAP` при заблокированной цели; если результат пуст — `NO_ELIGIBLE_TASKS`
или `BUDGET_TOO_SMALL` (допустимые задачи есть, но ни одна не помещается). Частичные
данные могут недооценить готовность или повторно предложить решённое за пределами
окна истории; это явно обозначается warning, а не скрывается как персонализация.

Изменение порогов/времени/ранжирования требует новой policy version и проверки
экспертных сценариев. Реальное качество обучения и delayed retention этим MVP не измерены.

## Проверяемые гарантии

Unit-сценарии проверяют холодный старт, три разных prerequisites, старые версии,
дубликаты, нейтральные ошибки, diversity, бюджет, deterministic replay и запрет
планового «открытия» зависимых тем. HTTP-проверки покрывают auth, actor, строгий
JSON, лимиты и безопасные ошибки; benchmark использует максимальный вход.
Первоначальный результат `practice-v1` записан в `docs/verification.md`; проверки
новой политики — в `docs/verification-v2.md`.

## Индивидуальный маршрут practice-v3

Необязательный `session_count` (1–8; отсутствие/0 = 1) задаёт горизонт.
Каждое занятие ограничено своим бюджетом и 20 задачами; повторов между занятиями нет.
`items`/`total_minutes` сохраняют значение первого занятия. `sessions` содержит весь
маршрут; `total_planned_minutes` — суммарное время. `topic_insights` объясняет
успешные решения, нерешённые ошибки, доступные задачи и транзитивную базу.
`SHORT_HORIZON` сообщает, что задач не хватило на весь горизонт. Плановые задачи
не становятся evidence. При равном покрытии тем база и практика после ошибок
получают приоритет. Остальные правила practice-v2 сохраняются.

Цель хранит `session_count` после миграции `202611090002`; старые записи получают 1.
Обновлять сначала recommendations с миграцией, затем gateway и frontend.
Календарных дат и подтверждённой оценки освоения нет.
